# Update Docs When Creating a PR

Analyze a PR being created to determine if customer-facing documentation updates are needed. If so, create a companion docs PR that can be merged after the source PR.

## When to Use

Invoke this skill automatically when helping create a PR, as the final step after the source PR is created.

## Context

- Docs repo: `tessl/docs`
- Current repo: The repository where the PR is being created
- Current branch: The branch being turned into a PR

## Step 1: Gather PR Information

Get information about the PR that was just created:

```bash
# If PR already exists for current branch
gh pr view --json title,body,commits,files,number,url

# Get the diff against main
git log main..HEAD --oneline
git diff main...HEAD --stat
```

## Step 2: Analyze for Documentation Impact

**Changes that REQUIRE doc updates:**
- New user-facing features (feat: commits with user impact)
- Breaking changes or API changes
- New CLI commands, flags, or options
- New configuration options or environment variables
- Changes to MCP tools
- Bug fixes that change documented behavior

**Changes that do NOT need doc updates:**
- Internal refactoring with no user-facing changes
- Test-only changes
- CI/CD pipeline changes
- Development tooling changes
- Dependency updates (unless they affect user requirements)
- Performance optimizations with no behavioral changes

## Step 3: Decision Point

**If NO documentation updates are needed:**
- Briefly explain why (internal changes, tests only, etc.)
- Stop here

**If documentation updates ARE needed:**
- Explain what needs updating
- Identify affected doc files:
  - `changelog.md` - for any user-facing change
  - `reference/` files - for CLI, config, MCP tool changes
  - `common-workflows/` - for new features that need tutorials
  - `introduction-to-tessl/` - for changes affecting getting started
- Proceed to Step 4

## Step 4: Update the Docs Repo

### 4.1 Clone the docs repo

```bash
DOCS_DIR=$(mktemp -d)
cd $DOCS_DIR
git clone git@github.com:tessl/docs.git .
```

### 4.2 Create a branch

Use naming convention: `docs/<source-repo>-<source-branch>`

```bash
git checkout -b docs/<source-repo>-<source-branch-name>
```

### 4.3 Make documentation updates

**For changelog.md:**
- Add entry under current version section
- Use categories: `### New Features`, `### Improvements`, `### Bug Fixes`, `### Breaking Changes`
- Format: `* **Feature Name** - Description of what it does`

**For reference docs:**
- Match existing file structure and formatting
- Use code blocks for commands and examples

### 4.4 Commit the changes

```bash
git add .
git commit -m "docs: update from <source-repo> PR #<number>

<brief description>

Source: <source-repo>#<number>"
```

### 4.5 Push and create PR

```bash
git push -u origin docs/<source-repo>-<source-branch>
gh pr create --title "docs: update from <source-repo> PR #<number>" --body "## Summary

This PR updates documentation based on changes from [<source-repo>#<number>](<source-pr-url>).

### Documentation Changes
<list the doc files updated and why>

### Source PR
- Repository: <source-repo>
- PR: #<number>
- URL: <source-pr-url>

---
**Merge this PR after the source PR is merged.**

Generated by update-docs skill"
```

### 4.6 Clean up and report

```bash
cd -
rm -rf $DOCS_DIR
```

Tell the user:
1. The URL of the created docs PR
2. Remind them to merge the docs PR after the source PR is merged
